# enco 设计文档

> 版本：v0.1（草案） · 日期：2026-11-12 · 许可证：Apache-2.0
> 参赛赛道：福州软件职业技术学院「AI+」应用能力大赛 · AI+编程赛道

## 1. 一句话定位

**enco 是一个运行在手机上的校园 AI 助手。你说一句话，它会自己规划步骤、操作手机上的 App 把事情办完，并且会记住你的习惯。**

和普通的对话式 AI 不同，enco 能真正“动手”：看懂屏幕，点击、滑动、输入，跨多个 App 完成任务。遇到付款、发消息、提交表单这类关键动作时，它会先停下来问你。

## 2. 背景与痛点（路演用）

| 痛点 | 现状 | enco 的做法 |
|---|---|---|
| 校园通知太分散 | 通知散落在 QQ 群、微信群、学习通、钉钉里，容易漏掉截止时间 | 通知雷达自动汇总，提取截止时间、地点和需要做的事 |
| 重复性手机操作多 | 每天查课表、签到、填问卷、找文件 | 一句话交给 enco 执行，成功的流程会沉淀成技能，下次更快 |
| 现有 AI 只能聊天 | 回答完还要自己去操作 | 多 Agent 协作，直接操作 App 把事情做完 |
| 隐私顾虑 | 很多助手要把数据上传到它们的服务器 | 没有 enco 服务器，数据保存在本机，模型由用户自己选择和配置 |

## 3. 设计原则

1. **可演示优先**：每个阶段都要有一个能在真机上稳定跑通的完整流程。决赛要求现场演示，稳定比功能多更重要。
2. **人始终在环**：涉及金钱、对外发送、不可撤销的操作，默认都要确认；任务运行中随时可以插话、暂停或停止。
3. **模型无关**：只依赖 OpenAI 兼容接口，不绑定任何厂商。
4. **原创实现**：只参考 upstream 中三个项目和学术论文的设计思路，不复制代码（见第 13 节）。
5. **过程可追溯**：每一步的屏幕、决策和结果都留档，既用于调试，也满足大赛的“规范性”评分。

## 4. 功能范围

### 4.1 核心功能（初赛必须完成）

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 对话 | 流式回复，支持 Markdown，任务过程以时间线展示 |
| F2 | 手机控制 | 读取界面、截图、点击、滑动、输入、返回、启动 App。主要通过 Shizuku 获得的 shell 权限完成；Shizuku 没有运行时，自动改用无障碍服务（只支持主屏） |
| F3 | 多 Agent 自主执行 | 规划者、执行者、反思者三个角色协作完成多步任务 |
| F4 | 悬浮球 | 全局悬浮，可以绑定快捷操作（截图、截图问 AI、语音指令等），任务进行中显示状态 |
| F5 | 安全确认 | 敏感动作先确认；支持“询问模式 / 自主模式”切换 |
| F6 | 长期记忆 | 记住用户画像和偏好，成功的任务沉淀为可复用技能 |
| F7 | 语音 | 按住说话（语音识别），结果语音播报（TTS） |
| F8 | 校园场景 | 通知雷达、课表识别与提醒、表单代填（详见第 10 节） |
| F9 | 模型配置 | 自定义 Base URL、API Key 和模型，可以分别设置文本模型和视觉模型 |
| F10 | 执行位置选择 | 每次发起任务时选择在**主屏**、**系统小窗**或**后台虚拟屏**执行；虚拟屏可以再开一个预览小窗实时观看，点一下就能接管（详见 7.3 节） |

### 4.2 增强功能（决赛前完成）

| 编号 | 功能 | 说明 |
|---|---|---|
| E2 | 定时与条件任务 | 例如“每天 7:30 查课表，有早八就提醒我” |
| E3 | 评测集 | 20 个标准任务，统计成功率、平均步数和耗时，作为技术答辩的数据支撑 |
| E4 | 任务回放 | 回放每一步的截图和决策，路演时可以作为备份展示 |

### 4.3 明确不做

- 抢课、刷课、自动签到代打卡这类违反学校规定或第三方服务条款的功能
- 自动完成付款或输入密码：这类页面一律交给用户接管
- iOS 和鸿蒙原生版本

## 5. 总体架构

```text
┌──────────────────────────────── UI 层（Jetpack Compose）────────────────────────────────┐
│  对话页 · Agent 时间线 · 记忆与技能管理 · 校园面板 · 设置（模型 / 权限 / 悬浮球）        │
└──────────────────────────────────────────┬──────────────────────────────────────────────┘
                                           │ StateFlow / 事件
┌──────────────────────────────── Agent 编排层（agent-core）──────────────────────────────┐
│  Orchestrator（状态机）                                                                  │
│    ├─ Planner   规划者：理解意图 → 检索记忆/技能 → 拆成子目标                            │
│    ├─ Operator  执行者：观察屏幕 → 选择下一个动作                                         │
│    ├─ Reflector 反思者：对比动作前后 → 判断成功/失败/卡住 → 纠错或重新规划                │
│    ├─ Guard     安全守卫：识别敏感动作 → 请求确认 / 交给用户接管                          │
│    └─ Curator   记忆管家：任务结束后提炼偏好，并把成功轨迹沉淀为技能                      │
└───────┬───────────────────────┬────────────────────────┬────────────────────────────────┘
        │                       │                        │
┌───────▼────────┐   ┌──────────▼──────────┐   ┌─────────▼──────────┐
│  LLM 层         │   │  设备层              │   │  记忆层             │
│  OpenAI 兼容    │   │  DeviceController    │   │  Room + FTS         │
│  流式 / 多模态  │   │  ├ Shizuku（主）      │   │  画像 · 会话 · 经验  │
│  JSON 动作解析  │   │  ├ 无障碍（备用）     │   │  技能 · 校园数据     │
└────────────────┘   │  ├ 主屏 / 小窗 / 虚拟屏│   └────────────────────┘
                     │  ├ 悬浮球 / 预览小窗  │
                     │  └ 语音 ASR / TTS     │
                     └──────────────────────┘
```

### 5.1 技术选型

| 领域 | 选型 | 理由 |
|---|---|---|
| 语言 / UI | Kotlin + Jetpack Compose | 原生系统能力最完整，Shizuku、悬浮窗和系统服务都能直接调用 |
| 系统权限 | Shizuku（API + UserService）为主，无障碍服务备用 | 免 Root，以 shell 身份运行助手进程，获得 ADB 级的手机控制能力；Shizuku 没运行时（例如手机刚重启）由无障碍服务兜底 |
| 最低版本 | minSdk 30（Android 11），targetSdk 36 | Android 11 起有“无线调试”，Shizuku 不用连电脑就能在手机上启动 |
| 并发 | Kotlin Coroutines + Flow | 任务可取消，状态流可以直接驱动 UI |
| 网络 | OkHttp + kotlinx.serialization | SSE 流式输出；JSON 动作解析 |
| 存储 | Room（含 FTS4）+ DataStore | 结构化记忆与全文检索；设置项 |
| 密钥 | Android Keystore（AES-GCM）加密后存入 DataStore | API Key 不明文落盘 |
| 后台任务 | WorkManager + 前台服务 | 定时任务；长任务保活 |
| 依赖注入 | 手写 ServiceLocator | 规模小，不引入 Hilt，减少构建复杂度 |

具体的库、版本号、构建配置和用法约定见 [tech-stack.md](tech-stack.md)。

### 5.2 工程结构

```text
enco/
├── app/                 Android 应用：UI、Service、平台实现
│   └── src/main/java/xyz/her3/enco/
│       ├── ui/          对话、时间线、设置、校园面板
│       ├── device/      Shizuku 与 shell 助手进程、无障碍服务、舞台、悬浮球、语音
│       ├── memory/      Room 实体、DAO、检索
│       ├── campus/      通知雷达、课表、表单
│       └── llm/         OpenAI 兼容客户端
├── agent-core/          纯 Kotlin/JVM 模块：编排器、各 Agent、Prompt、动作协议
│                        不依赖 Android，可以在电脑上用 JUnit 快速测试
├── eval/                评测任务集与结果
└── docs/                设计、排期、开发日志、第三方声明
```

`agent-core` 只通过接口（`DeviceController`、`LlmClient`、`MemoryStore`）访问外部能力，测试时可以注入假实现，在电脑上回放录制好的屏幕数据验证 Agent 逻辑。

## 6. 多 Agent 协作设计

### 6.1 主循环

```text
用户指令
  │
  ▼
Planner：检索画像、相关技能和历史经验 → 输出计划（子目标列表）
  │
  ▼
┌─► Operator：读取当前屏幕 → 输出一个动作
│     │
│     ▼
│   Guard：是否属于敏感动作？ ── 是 ──► 请求用户确认 / 交给用户接管
│     │ 否 / 已确认
│     ▼
│   DeviceController 执行动作，等待界面稳定
│     │
│     ▼
│   Reflector：对比动作前后的屏幕
│     ├─ 成功且子目标完成 → 进入下一个子目标
│     ├─ 成功但未完成     → 继续当前子目标
│     ├─ 失败             → 把失败原因交给 Operator 重试（最多 3 次）
│     └─ 卡住 / 偏离计划   → 交回 Planner 重新规划
└─────┘
  │ 全部完成或达到步数上限
  ▼
Curator：生成总结 → 提炼用户偏好 → 成功轨迹沉淀为技能
```

### 6.2 角色职责

| 角色 | 输入 | 输出 | 模型 |
|---|---|---|---|
| Planner | 用户指令、用户画像、检索到的技能和经验、已安装 App 列表 | 子目标列表与成功判据 | 文本模型 |
| Operator | 当前子目标、屏幕元素列表、标注截图、最近几步历史 | 一个结构化动作 + 简短理由 | 视觉模型 |
| Reflector | 动作、动作前后的屏幕摘要 | 成功 / 失败 / 卡住 + 原因 | 视觉或文本模型 |
| Guard | 动作及其目标元素 | 放行 / 需确认 / 需接管 | 规则优先，必要时调用模型 |
| Curator | 完整轨迹与对话 | 偏好条目、技能草稿、任务总结 | 文本模型 |

为了控制成本和延迟：Reflector 先用规则判断（界面是否变化、目标元素是否出现），判断不了才调用模型；Guard 以关键词和控件语义规则为主。

### 6.3 动作协议

Operator 必须输出 JSON，由 `agent-core` 校验后再执行：

```json
{
  "thought": "搜索框在顶部，先点击它",
  "action": "tap",
  "target": 12,
  "expect": "出现输入法与搜索建议"
}
```

| 动作 | 参数 | 说明 |
|---|---|---|
| `tap` / `long_press` | `target`（元素编号）或 `x,y`（0–1000 归一化坐标） | 优先用元素编号，失败时退回坐标 |
| `type` | `target`, `text`, `submit?` | 将完整文本放入剪贴板，粘贴到已聚焦的目标输入框 |
| `swipe` | `direction`, `distance?`, `target?` | 滚动列表或翻页 |
| `back` / `home` | 无 | 系统导航 |
| `launch` | `app`（名称或包名） | 直接启动 App，比在桌面找图标更稳 |
| `wait` | `ms` | 等待加载 |
| `ask_user` | `question` | 信息不足时向用户提问 |
| `take_over` | `reason` | 登录、验证码、付款等场景交给用户 |
| `remember` | `fact` | 写入长期记忆 |
| `finish` | `summary`, `success` | 结束任务并汇报 |

### 6.4 屏幕感知

同时提供两种信息，互相补充：

1. **元素列表**：把 shell 助手进程读到的控件树压缩成编号列表，只保留可见、可交互或带文字的节点。每个元素记录编号、类型、文字/描述、可点/可滚动/可编辑，以及归一化坐标。一般能从上千个节点压缩到 50–150 行。
2. **标注截图**：在截图上给每个元素画框并写上编号（Set-of-Mark 思路），缩放到长边 1280 后再发送，帮助视觉模型把“看到的”和“能操作的”对应起来。

控件树缺失时（例如游戏、Flutter 或 WebView 自绘界面），只发截图，让模型输出坐标。

### 6.5 中断与插话

- 任务运行时，用户的新消息进入**插话队列**，每一步开始前都会合并进 Operator 的上下文。
- 停止：立即取消协程，并汇报“已完成到哪一步”；用户说“继续”时，从记录的断点恢复。
- 循环保护：连续 3 步屏幕没有变化，或在相同的几个状态之间来回切换，就判定为卡住，交回 Planner。
- 硬性上限：单个任务默认最多 40 步、10 分钟，可以在设置中调整。

## 7. 设备层

### 7.1 后端抽象

```kotlin
interface DeviceController {
    suspend fun open(stage: StageRequest): Stage  // 按执行位置准备主屏 / 小窗 / 虚拟屏
    suspend fun observe(): Observation            // 当前执行位置内的元素列表 + 截图 + 当前 App
    suspend fun perform(action: Action): ActionResult
    suspend fun launchApp(query: String): ActionResult
    suspend fun close(keepApp: Boolean)           // 任务结束：释放虚拟屏 / 小窗
    val capabilities: Set<Capability>             // 当前可用的能力，用于自动降级
}
```

`agent-core` 看到的永远是一块“舞台”（Stage）：坐标都按舞台归一化到 0–1000，截图和元素列表也只包含舞台里的内容。所以主屏、小窗、虚拟屏三种执行位置对 Agent 完全透明，Prompt 和动作协议不用区分。

有两个实现，按可用性自动选择：

| 优先级 | 实现 | 条件 | 能力 |
|---|---|---|---|
| 1 | `ShizukuDevice` | Shizuku 正在运行并已授权 | 全部能力，支持主屏、小窗、虚拟屏三种执行位置 |
| 2 | `A11yDevice` | Shizuku 没运行，但 enco 的无障碍服务已开启 | 只支持主屏；读界面、截图、手势、输入文字、返回、启动 App |
| 3 | 无 | 两者都不可用 | 只聊天；悬浮球的截图功能不可用，并引导用户开启 |

Shizuku 恢复运行后自动切回 `ShizukuDevice`。任务进行中不切换后端，避免同一个任务前后行为不一致。

### 7.2 设备后端：Shizuku 为主，无障碍备用

```text
enco App 进程                                shell 助手进程（uid 2000，由 Shizuku 启动）
┌──────────────────────────┐   Binder/AIDL   ┌───────────────────────────────────┐
│ ShizukuDevice            │ ──────────────► │ UiAutomation：控件树、截图、        │
│ （实现 DeviceController） │                 │   注入触摸与按键、设置文字          │
└──────────────────────────┘                 │ 系统命令：am / pm / appops / cmd   │
                                             └───────────────────────────────────┘
```

- 助手进程通过 Shizuku 的 UserService 启动，代码就打包在 enco 的 APK 里，以 shell 身份常驻，并通过固定的 AIDL 接口和 App 通信。
- 读界面、截图、注入手势都在助手进程里通过 `UiAutomation` 完成，不需要每一步都执行 `uiautomator dump`、`screencap`、`input` 这些命令（每次要 0.5–2 秒）。这些命令只作为兜底。
- 连接 UiAutomation 时带上 `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`，不影响用户已经开启的其他无障碍服务（例如读屏软件）。

| 能力 | 主要实现 | 兜底 |
|---|---|---|
| 读取控件树 | `UiAutomation` 读取当前窗口节点 | `uiautomator dump` |
| 截图 | `UiAutomation.takeScreenshot` | `screencap -p` |
| 点击 / 长按 / 滑动 | `UiAutomation.injectInputEvent` | `input tap` / `input swipe` |
| 输入文字 | 写入临时剪贴板后执行粘贴，完成后恢复原剪贴板 | 输入框未暴露粘贴动作时注入系统粘贴键 |
| 返回 / 主页 | 注入按键事件 | `input keyevent` |
| 启动 App | `am start` / `monkey -p` | – |
| 被 `FLAG_SECURE` 保护的页面 | 截图为黑屏，交给用户接管 | – |

粘贴前必须能读取并安全保存原纯文本剪贴板；Android 限制读取原正文时取消操作，避免覆盖后无法恢复。临时剪贴板带所有权标记，只恢复仍归 enco 所有的内容，不覆盖用户在此期间的新复制内容。

**一键授权**：有了 shell 权限后，enco 可以自动开启其他权限，用户不用逐个去系统设置里找：

| 权限 | 命令 |
|---|---|
| 悬浮窗（悬浮球） | `appops set <包名> SYSTEM_ALERT_WINDOW allow` |
| 读取通知（通知雷达） | `cmd notification allow_listener <组件名>` |
| 通知、录音等运行时权限 | `pm grant <包名> <权限>` |
| 电池优化白名单 | `dumpsys deviceidle whitelist +<包名>` |
| 无障碍服务（备用后端） | `settings put secure enabled_accessibility_services`，在原有列表后追加 enco 的服务，不动用户已开启的其他服务 |

**Shizuku 的启动与状态**

- 用户需要安装 Shizuku App，并在其中通过“无线调试”启动（Android 11+，不需要电脑）；也可以用 USB 连接电脑，执行一条 adb 命令启动。
- 手机重启后（部分系统在关闭无线调试后也会）需要重新启动 Shizuku。enco 每次打开时都会检测 Shizuku 和助手进程的状态，未运行时引导用户一键跳转到 Shizuku。
- Shizuku 未运行时，自动改用无障碍备用后端；两者都不可用时，enco 退化为只聊天模式。
- 助手进程只开放固定的几类接口（读界面、截图、注入输入、启动 App、给 enco 自己授权），**不提供任意 shell 命令执行**，模型也无法直接运行命令。

#### 无障碍备用后端

保证 Shizuku 没运行时（最常见的是手机重启后），悬浮球截图和主屏任务仍然可用。

| 能力 | 实现 |
|---|---|
| 读取控件树 | `getWindows()` / `rootInActiveWindow` |
| 截图 | `AccessibilityService.takeScreenshot`（Android 11+，enco 自己拿到图片，不调用系统截图） |
| 点击 / 长按 / 滑动 | `dispatchGesture` |
| 输入文字 | 写入剪贴板后执行 `ACTION_PASTE` |
| 返回 / 主页 | `performGlobalAction` |
| 启动 App | 由无障碍服务启动 App 的启动 Intent |
| 小窗 / 虚拟屏 | **不支持**，执行位置选择器里这两项置灰，提示“需要 Shizuku” |

- **开启方式**：Shizuku 运行时，由助手进程自动开启无障碍服务，并在服务被系统停掉时自动重新开启。这样也绕开了 Android 13+ 对非应用商店安装的 App 的“受限制的设置”拦截。从没启动过 Shizuku 的用户，引导页会教他手动开启：先在“应用信息”右上角菜单里点“允许受限制的设置”，再去无障碍设置里打开 enco。
- **两者并存**：Shizuku 运行时，读界面和操作仍然走 shell 助手进程，无障碍服务只保持待命，不重复干活。助手进程连接 UiAutomation 时带 `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`，不会把 enco 自己的无障碍服务挤掉。
- **截图**：两个后端截出的都是 `Bitmap`，悬浮球的“截图”和“截图问 AI”统一走 `DeviceController`，不关心当前用的是哪个后端。

### 7.3 执行位置：主屏 / 小窗 / 虚拟屏

发起任务时，输入框旁边有一个“执行位置”选项，默认记住上次的选择。当前手机不支持的选项会置灰，并说明原因。

| 执行位置 | 效果 | 实现 | 系统要求 |
|---|---|---|---|
| **主屏** | 直接在当前屏幕上操作，用户看着它做，期间不能用手机 | 在主屏读界面、注入输入 | Android 11+ |
| **系统小窗** | 目标 App 以小窗形式浮在主屏上，用户能看着它操作，同时可以在小窗外使用其他 App | `am start --windowingMode 5` 以自由窗口模式启动，并设置窗口位置和大小；读界面时只取这个窗口，截图按窗口区域裁剪，坐标按窗口换算 | 系统支持自由窗口（部分国产系统自带小窗，原生系统需要开启开发者选项里的“自由窗口”） |
| **虚拟屏** | 任务在一块看不见的后台屏上执行，完全不影响用户用手机 | 助手进程创建虚拟屏，用 `am start --display <编号>` 把 App 启动到虚拟屏上；读界面取该屏的窗口，输入事件带上该屏编号 | Android 12+；**Android 14+ 推荐**（虚拟屏有独立焦点，不会抢走主屏的输入） |

**虚拟屏的实现要点**

- 助手进程以 shell 身份创建虚拟屏，尺寸和主屏一致，画面输出到 `ImageReader`。截图直接从这里取最新一帧。
- 创建时带上独立焦点（Android 14+）、受信任、内容随屏销毁等标志，保证 App 能正常启动并接收输入。
- 输入文字使用剪贴板粘贴到目标舞台中已聚焦的输入框，避免输入法改写文本。
- 任务结束时，按用户选择把 App 移回主屏（“在主屏打开结果”），或者随虚拟屏一起关闭。

**预览小窗**（仅虚拟屏模式，可开关）

- 一个可拖动、可缩放的悬浮窗口，实时显示虚拟屏画面（从 `ImageReader` 取帧，缩小后约每秒 5–10 帧）。
- 点击放大；点“接管”后把 App 移到主屏，交给用户亲手操作，操作完点“继续”再交回 enco。
- 需要确认或接管时（例如付款、验证码），即使预览小窗关着也会自动弹出，同时任务状态条显示警告色。

**自动降级**：选中的执行位置失败时（例如 App 拒绝在虚拟屏上启动、小窗启动后不是自由窗口），提示用户并自动改到主屏执行，不让任务直接失败。

### 7.4 快捷悬浮球与任务状态

悬浮球使用悬浮窗显示：无障碍服务开启时用 `TYPE_ACCESSIBILITY_OVERLAY`，不需要悬浮窗权限；否则用 `TYPE_APPLICATION_OVERLAY`，所需的悬浮窗权限由 shell 助手进程自动授予。两种情况用户都不用手动去设置里开悬浮窗权限。

截图优先用 Shizuku 助手进程，Shizuku 没运行时用无障碍服务，两者都不可用时点击悬浮球会提示开启方法。

**当前窗口分工**

- 快捷悬浮球：有悬浮窗权限时，打开 App 或从授权页返回即默认显示，空闲时也保留。使用独立的截图图标，可拖动并在松手后吸附到屏幕左右边缘。
- 手机任务状态条：只在任务运行、等待确认或展示结果时出现在顶部，显示阶段、确认、停止和结果关闭，不与快捷球互相变形。关闭结果只隐藏状态条，聊天页仍保留结果详情。
- 任务成功时，在当前应用上方显示「任务完成」，绿色亮边沿胶囊轮廓循环。点击胶囊或屏幕其他位置收起。系统设置任务也发送短时系统通知，为可能隐藏第三方悬浮窗的页面提供提示。

**手势与快捷操作**

| 手势 | 操作 |
|---|---|
| 单击快捷球 | 日程截图问 AI 的预留入口；当前只提示后续接入，不截图、不上传 |
| 双击快捷球 | 后续可扩展为其他截图问答 |
| 长按快捷球 | 后续可扩展为语音指令 |
| 拖动快捷球 | 移动位置；松手后自动吸附到屏幕边缘 |
| 点击任务状态条 | 等待确认时打开确认卡片；终态时关闭结果 |

后期单击快捷球时，在统一的悬浮窗隐藏与恢复流程中截取主屏，将图片通过一次性图片请求发给模型，再由校园模块把文本结果整理为日程草稿，经用户确认后保存。截图和日程解析不借用手机任务状态机。

**状态显示**：快捷球不承担任务状态。任务状态条区分执行中、等待确认、完成、失败和停止；等待确认时点击状态条打开确认卡片。

截图或注入触摸前会同时隐藏快捷球和任务状态条，避免它们被截进图里或遮挡触摸目标，结束后恢复。

### 7.5 语音

- 识别：优先使用系统 `SpeechRecognizer`。如果手机没有系统识别服务（部分国产手机），退回到所配置模型服务商的 `/audio/transcriptions` 接口。
- 播报：系统 `TextToSpeech`。默认只在用户用语音发起任务时才播报结果，可以在设置中关闭。

## 8. LLM 层

- 只依赖 **OpenAI Chat Completions 兼容接口**，图片以 base64 `image_url` 传入。
- 聊天使用同一个流式请求接收自然语言或 `phone_control` 调用。客户端收齐并校验原生 `tool_calls` 后请求本次授权，复用前台任务服务与 Guard。任务结束后用对应的 `tool_call_id` 回传状态并继续当前回复。Gmail 邮件明细仅保留在本机的聊天气泡中。
- 有本轮结果可查时，模型可调用 `open_task_result` 打开 enco 聊天。只需完成提示的任务留在当前应用。系统阻止自动切换时，悬浮状态条提供「查看任务结果」入口。
- 设置项：Base URL、API Key、文本模型、视觉模型（可以相同）、温度、超时。提供“测试连接”按钮。
- 动作输出：优先使用 `response_format: json_object`；服务商不支持时，从回复中提取 JSON 并按 schema 校验，失败最多重试 2 次。
- 文档中给出几个经过验证的配置示例（例如通义千问、智谱、豆包、DeepSeek + 任一视觉模型），但代码中不写死任何厂商。
- 每次调用都记录 token 用量和耗时，在任务详情中展示。

## 9. 记忆层

### 9.1 三级记忆

| 层级 | 内容 | 使用方式 |
|---|---|---|
| 核心画像 | 姓名、学号、专业、班级、常用 App、偏好（如“外卖不要香菜”） | 每次规划时全部注入，控制在 1–2K token |
| 近期会话 | 最近 72 小时的对话摘要 | 按时间注入最近几条 |
| 经验与技能 | 历史任务轨迹、沉淀的技能 | 按相关度检索前 3 条 |

### 9.2 技能

成功完成的任务由 Curator 整理成技能：

```text
名称：查看学习通未交作业
触发描述：学习通 作业 没交 截止
适用 App：com.chaoxing.mobile
步骤要点：打开学习通 → 底部“我的” → “作业” → 筛选“未完成”
注意事项：首次进入会弹出更新提示，需要先关闭
统计：成功 5 次 / 失败 1 次，平均 9 步
```

下次遇到类似任务时，Planner 会把技能作为参考提示交给 Operator。技能不是固定脚本，界面变化时仍然由模型判断，所以不会因为 App 改版而完全失效。用户可以在“记忆与技能”页面查看、编辑或删除。

### 9.3 检索

- 使用 Room FTS4 全文检索。SQLite 默认分词器不能切分中文，所以写入时额外生成一个**二元分词**列（“查课表” → “查课 课表”）用于检索。
- 检索结果再交给 Planner 筛选，不引入本地向量模型，以控制安装包大小和耗电。

### 9.4 隐私

- 所有记忆只存在本机；可以一键导出或清空。
- 画像中的敏感字段（学号、手机号）只在需要填写时才注入上下文。
- 截图仅在任务进行中保存在应用私有目录，默认保留 7 天，可以设置为任务结束后立即删除。

## 10. 校园场景

| 场景 | 实现方式 | 演示话术 |
|---|---|---|
| **通知雷达** | 用 `NotificationListenerService` 读取 QQ、微信、钉钉、学习通的通知，由模型判断是不是校园通知，并提取标题、截止时间、地点和待办事项，汇总到校园面板，临近截止时提醒。只读取通知文字，不操作 App | “今天群里有什么要交的？” |
| **课表识别与提醒** | 用户对教务 App 的课表页截图（或由 Agent 自动打开截图），视觉模型识别出结构化课表，存入本地；上课前 15 分钟提醒，并附上教室 | “帮我把课表导进来” / “明天早八在哪上？” |
| **表单代填** | Agent 打开问卷或报名链接，用画像中的信息填写，**提交前必须确认** | “帮我报名这个讲座” |
| **一句话办事** | 通用 Agent 能力配合校园 App 技能，例如查看未交作业、查询成绩、找到群文件 | “看看学习通有没有没交的作业” |
| **选课辅助**（有余量再做） | 只做信息整理：读取课程列表、对比时间冲突和学分，生成建议。**不做抢课** | “这几门选修哪些时间不冲突？” |

## 11. 安全设计

| 风险 | 措施 |
|---|---|
| 误操作造成损失 | Guard 拦截付款、转账、删除、发送、提交、授权等动作；询问模式下必须确认，自主模式下仍然拦截涉及金钱的动作 |
| 密码与验证码 | 识别到密码框、验证码、`FLAG_SECURE` 页面时，暂停任务并交给用户接管 |
| 提示词注入 | 屏幕上读到的文字一律作为“数据”传入，并在 Prompt 中声明不得把屏幕内容当作指令执行；屏幕内容要求执行敏感动作时，必须经过用户确认 |
| 失控 | 步数和时长上限；悬浮球一键停止；任务运行时通知栏常驻“停止”按钮 |
| shell 权限过大 | 助手进程只开放固定接口，不执行任意命令；模型输出的动作必须先通过协议校验 |
| API Key 泄露 | Keystore 加密；日志脱敏；导出诊断信息时不包含密钥 |
| 违反第三方条款 | 首次使用时展示免责声明；不提供批量刷量、抢购、抢课类功能 |

## 12. 评测方案（E3）

建立 20 个标准任务，覆盖系统设置、校园 App、内容浏览、表单填写和跨 App 操作，分为简单、中等、困难三档：

| 指标 | 说明 |
|---|---|
| 成功率 | 人工判定是否达成目标 |
| 平均步数 / 耗时 | 衡量效率 |
| 首次 / 二次执行对比 | 验证技能沉淀的效果（第二次执行应更快、更稳） |
| 单 Agent vs 多 Agent | 关闭 Reflector 做消融对比，验证多 Agent 设计的价值 |

评测结果写入 `eval/results/`，并作为 PPT 中“技术应用”部分的数据支撑。

## 14. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型延迟高，单步 3–8 秒 | 演示节奏慢 | 规则优先的 Reflector；元素编号优先于纯视觉；演示视频适当加速并标注倍速 |
| 部分 App 控件树为空 | Agent 看不懂界面 | 退回到纯截图 + 坐标模式；演示时优先选择控件树完整的 App |
| Shizuku 没有运行（重启后、无线调试关闭后） | 无法操作手机 | 每次打开 App 都检测并引导启动；演示前按检查清单确认；自带手机热点，保证无线调试可用 |
| 国产 ROM 限制 | 小米/红米需要开启“USB 调试（安全设置）”才允许注入触摸；部分系统会杀后台，或停掉无障碍服务 | 启动时自检触摸注入能力，失败时按机型给出引导；前台服务保活；自动加入电池优化白名单；无障碍服务被停掉时由 Shizuku 自动重新开启 |
| 现场网络不稳定 | 演示失败 | 自带手机热点；准备备份演示视频；保留任务回放功能 |
| 虚拟屏 / 小窗兼容性 | Android 12、13 上虚拟屏可能短暂抢走主屏焦点；少数 App 拒绝在虚拟屏上运行或显示黑屏；各家系统的小窗实现不同 | 启动前按系统版本检测并置灰不支持的选项；运行中失败自动降级到主屏；演示用的 App 提前在测试机上验证三种模式 |
| 工期紧张 | 功能做不完 | 严格按排期冻结功能；增强功能全部放到决赛前 |
